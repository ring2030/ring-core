# ring-core PoC 仕様（コンテスト向け・高校生向け）

## 1. このPoCで解決すること

今の課題は「どの病院のデータか分からない」「誰が見てよいか分からない」です。

このPoCでは次を最低限実現します。

- 病院Aのデータは病院Bから見えない
- 看護師ログインごとに所属病院が決まる
- 既存画面はなるべく変えない
- `ID=1 / PASS=1` はこれまで通り使える

## 2. たとえ話で理解する

- **病院ごとの切り分け**: 学校ごとに別の下駄箱を用意する
- **看護師ごとのログイン**: 下駄箱の鍵を持つ人だけ開けられる
- **API強制フィルタ**: 鍵が合う下駄箱しか開かない仕組み

## 3. PoCで作る最小機能

### 3-1. ログイン

- 看護師がID/PASSでログイン
- サーバー側で `hospitalId` を決める
- セッションに `hospitalId` を保存する

### 3-2. データ分離

- Firestoreのコレクションを病院単位で分ける
- ただし既存デモ互換のため、`ID=1` は従来の `calls` を利用
- 他病院は `calls__{hospitalId}` を利用

### 3-3. 招待リンク

- 家族/患者向け招待トークンに `hospitalId` を埋め込む
- 招待でログインした先でも同じ病院スコープに入る

### 3-4. APIガード

- スタッフ系画面アクセス時は `role=nurse` かつ `hospitalId` 必須
- 家族/履歴画面アクセス時も `hospitalId` 必須

## 4. 今回「やらないこと」（PoCなので後回し）

- 役割の細分化（師長、一般看護師、閲覧専用など）
- 監査ログの本格保存
- 病院管理画面（病院作成、メンバー招待）
- セキュリティ強化（MFA、SSO、鍵管理）

## 5. 受け入れ条件（これができたらPoC合格）

- `ID=1 / PASS=1` で既存の見た目と操作感がほぼ維持される
- 病院IDがセッションに入り、画面が病院スコープで動く
- 招待リンク経由でも病院スコープが維持される
- サインアウトで病院情報も消える

## 6. 将来のエコシステム案

- **Identity**: ユーザー、病院所属、ロール管理
- **Access Control**: APIごとの権限判定
- **Clinical Data**: コール、ノート、動画メッセージ
- **Audit**: 誰が何を見たかの記録
- **Admin Portal**: 病院管理者の運用画面

このPoCは、上のエコシステムへ育てるための「土台」です。
